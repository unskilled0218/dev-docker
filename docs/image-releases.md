## Commands

```bash
bash build-all.sh --validate
bash build-all.sh --build-only
bash build-all.sh
```

Validation needs Bash and Python 3.11+ only. It reads local settings, version, notes, and source paths without credentials, locks, temporary files, Docker, or network access. Commands work from any directory.

No arguments publishes root `VERSION` as `v<VERSION>` and `latest` for all images. Update `VERSION`, `scripts/release.json`'s notes path, and matching committed release notes together; commit and push clean `main` before publication. Historical notes remain in `docs/releases/`; README has no duplicate version source.

`--help` and `-h` show usage using Bash only. A positional tag is deprecated but accepted only when it exactly equals `v<VERSION>`, with or without `--build-only`, in either order. Mismatched tags (including explicit `latest`), duplicate tags/flags, unknown flags, and help/validation combined with other arguments are refused before external effects. There is no arbitrary-tag publication override.

## Settings and prerequisites

Review `scripts/release.json` before use. Its strict schema names this repository (`https://git.lan`, `dev/dev-docker`), login, credential/certificate paths, notes, AMD64 platform, and the ordered two-image graph. Unknown/duplicate fields, path traversal, symlink source files, changed graph order/parents, and unsupported platforms are refused. There is no runtime download or self-update of release tooling.

Only `base` and `npm` build or publish, in that order. Release names are `git.lan/dev/base` and `git.lan/dev/npm`; npm uses the verified base digest, not a mutable parent tag. Both receive `v<VERSION>` and `latest` aliases. Package association is explicitly verified; OCI source labels alone do not establish repository visibility. No reassignment occurs.

Android, Tauri, and Switchboard are excluded from both modes, validation prerequisites, release inventories, staging, tag identities, and package links. Their Dockerfiles remain for manual builds with explicitly available parents: Android defaults to `npm:latest`; Tauri/Switchboard default to a manually built `android:latest`. The automated script does not produce that Android parent. Old package names, excluded packages, and historical aliases remain untouched; this is not a remote migration or cleanup command.

Publication requires Git, curl, Docker Buildx, a reachable selected builder advertising `linux/amd64`, independent Git authentication, trusted HTTPS, and a clean, already-pushed `main`. Fetch and push origins must each identify the configured project; multiple destinations are refused. The script never pushes source. One operator must exclude all other writers across the repository, two images, and their package associations; a checkout lock is not a distributed lock.

Build-only uses current Dockerfiles and needs neither clean `main` nor remote Git checks. It requires the selected Buildx builder to use the `docker` driver and the same Docker endpoint/image store as local image inspection. Select a supported builder explicitly before running. Container-backed, remote, Kubernetes, unknown, or mismatched builders are refused before builds; the command never creates/switches builders or pushes as a fallback. Each parent is loaded and its local ID checked before and after building children with its local tag and `--pull=false`. A local image ID is a config digest, not a registry manifest reference; do not pass it directly as a BuildKit `FROM`. Local `image:latest` names remain available for existing Compose/Dockerfile defaults. Publication does not load local images; run build-only separately if needed. Exclude concurrent local image writers while building.

Only AMD64 is supported by the release contract; this change does not certify other architectures or redesign image toolchains. The command installs no tools, certificates, privileged emulation, or dependencies on the host. Provide missing prerequisites separately; certificate installation happens only inside the built image.

## Credentials and trust

Credential-file precedence is nonempty `GIT_TOKEN`, then nonempty deprecated `FORGEJO_TOKEN_FILE`, then configured `token_file`, which defaults to `~/.config/git/token`. These variables contain file paths, never token values. Username precedence is nonempty `GIT_USERNAME`, then nonempty deprecated `FORGEJO_USERNAME`, then configured `username`. Empty overrides are treated as unset.

Use a non-symlink, user-owned regular token file outside the repository, mode 0600 or 0400, containing a private repository/package-capable token. Never commit it or place it in command arguments, shell history, `.env`, build contexts, or logs. Both publication and build-only need it because the current base Dockerfile requests BuildKit secret ID `token` at `/home/container/.config/git/token`. The secret value goes to Docker login via stdin and to builds only through a private BuildKit secret file. The base setup's secret-mounted command currently only creates a directory; this release migration does not redesign that setup.

Both build modes require two existing, nonempty certificate files, each at most 1 MiB. Git's `certificate_file` defaults to `/usr/local/share/ca-certificates/git.lanCA.crt`; override with `BUILD_CERT_FILE`. The `ntfy_certificate_file` defaults to `/usr/local/share/ca-certificates/ntfy.lanCA.crt`; override with `BUILD_NTFY_CERT_FILE`. Empty overrides use the configured paths; `~` expands to the caller's home and relative paths resolve from the caller's working directory. Missing, unreadable, empty, or oversized inputs stop before builder operations, credential loading, or publication writes. `--validate` checks configuration without reading either certificate.

Captured bytes enter the private build context as `git.lanCA.crt` and `ntfy.lanCA.crt`. The base Dockerfile copies both into `/usr/local/share/ca-certificates/` before `update-ca-certificates`; npm inherits this image trust. For manual base builds, supply both filenames at the context root alongside the Dockerfile directory and keep the existing BuildKit token secret requirement. Provide valid CA certificates separately; the script does not download or commit them.

The release certificate fingerprint is SHA-256 of canonical JSON mapping each context filename to its individual SHA-256 hash. It binds both files through the existing release identity field and OCI label; publication guards recheck both original inputs. Snapshots always use captured bytes. This fingerprint differs from the previous Git-only hash: use a new release version, and do not adopt or rewrite old staging evidence, tags, or completed releases.

Image trust does not configure the host's Git, curl, Docker daemon, or builder HTTPS trust. Keep verification enabled and provide host trust separately. No TLS bypass or automatic host trust installation occurs.

Publication uses a private mode-0700 temporary directory with minimal Docker auth and copied connection metadata, never inherited registry helpers/auth. Original config-local CLI plugin discovery and Buildx state paths are preserved; Docker host/context and TLS environment variables remain selected. Relative paths keep caller working-directory semantics. Normal failure/exit/signals remove only run-owned temporary files, not images or remote records. SIGKILL cannot perform cleanup; inspect leftovers privately without broad deletion.

## Repository package visibility

Publication supports the explicitly characterized upstream Gitea versions `1.24.7` and `28.2.0` only. A read-only implementation-time probe of `https://git.lan/api/v1/version` reported `28.2.0`; that is not proof of credentials, image builds, or publication readiness. Other versions, custom/forked version strings, and missing/malformed version responses stop before login or staging writes. Characterize a new contract and add matching tests before extending the supported set; do not downgrade the server or bypass TLS/authentication to force publication.

Use the individual namespace owner's token: the authenticated `/api/v1/user` and `/api/v1/users/dev` IDs and logins must match, the owner must be active, unrestricted, and permitted to log in, and the effective registry login must be `dev`. Gitea `28.2.0` additionally exposes `type`, which must be `User`; `1.24.7` does not expose it. Organization/delegate/admin-as-another-owner workflows are intentionally unsupported. Existing token scopes must include `read:user`, `write:repository` (which covers repository reads and release creation), and `write:package` (which covers package reads and linking), with access to private resources where required. The script never changes token scopes or server settings.

The repository read must prove exact repository/owner IDs and `dev/dev-docker`, boolean `has_packages: true`, and boolean `permissions.admin: true`. If Packages are disabled, enable the repository's Packages unit yourself before publication. Verified owner authority is captured privately and rechecked before mutations and completion. A permission-filtered `repository: null` is never enough on its own: only the characterized individual owner has complete association visibility for this namespace.

For each release image, the script first reads `GET /api/v1/packages/dev/container/{name}?page=1&limit=100`. Gitea `1.24.7` can return `200 []` for a missing package; `28.2.0` resolves the named package in middleware and returns HTTP 404 before listing versions if it does not exist. A successful empty first page means no non-internal versions. Nonempty listings continue to a confirmed empty page within inventory limits. Every version must match owner/name/type, have a unique positive integer version ID and version string, and expose a consistent repository association. Different versions have different IDs. Missing fields, conflicting associations, foreign repositories, or uncertain reads stop without mutation authority.

An initial named-package HTTP 404 is not proof of absence. Only after the authority checks above succeed, the script independently reads `GET /api/v1/packages/dev?type=container&q={name}&page=1&limit=100` through a confirmed empty page. Both supported versions search all matching non-internal versions for the verified individual owner. Every page must be an authorized HTTP 200 JSON array with valid owner/type/version identities and no duplicates. The name search is case-insensitive and non-exact: valid neighboring names are checked but not adopted or mutated. An exact target, including a case variant, contradicts the named-package 404 and stops publication. Absence is established only when the complete successful search has no exact target; shared byte/time/page/item budgets still apply. An owner-list 404, permission error, transport failure, malformed response, incomplete inventory, or named-list 404 after an observed version remains a refusal.

First publication needs neither a prior `--build-only` run nor manually created packages. After successful read-only startup checks, the existing staging builds/pushes create `base` and `npm`; fresh exact version reads must then prove their associations before linking and final publication. Absence is not cached across guards and cannot confirm a link or authorize completed-release repair. These listings exclude internal versions and do not prove that no internal-only or versionless record exists; existing conflict/refusal rules still apply.

After both staging images verify, publication links only genuinely unlinked packages with `POST /api/v1/packages/dev/container/{name}/-/link/dev-docker`, requiring `201` and fresh exact verification. Correct existing links are skipped. The characterized server services enforce equal package/repository owners and refuse already-linked packages; the script never unlinks or forces reassignment. An internal-only or versionless existing record can still cause a safe link refusal even when its version listing was empty. Reads and writes are not atomic; maintain single-operator exclusion.

Both associations must verify before tag publication, release creation, and final success. Completed-release retries are read-only and refuse missing/foreign links rather than repairing them. Before tag publication, a failed fresh attempt can retain verified staging images and confirmed links; its next fresh retry verifies them and skips existing correct links. A lost link response is reconciled only after this invocation attempted that POST and a fresh read proves the exact target association. Unresolved results stop without rollback. Neither `--validate` nor `--build-only` calls package APIs.

After separately authorized publication, inspect [the repository Packages page](https://git.lan/dev/dev-docker/packages) for `base` and `npm`. Association applies to the entire container package, not just one tag. Existing old or excluded packages are not removed or unlinked, so the page may also contain previously associated packages.

## Build proxies

Publication preserves validated `proxies` settings from the caller's Docker configuration in its private Docker config (directory mode 0700, file mode 0600). The complete map, including `default` and per-daemon entries, is copied without merging, endpoint guessing, or value expansion. Docker remains responsible for selecting default/endpoint settings and forwarding predefined proxy build arguments. Original config bytes remain unchanged; build-only uses the original config directly.

Absent or JSON-null `proxies` means no configured proxies. Empty maps, empty per-daemon maps, and explicit empty string values are retained. Endpoint keys must be nonempty control-free strings; each entry must be a map containing only `httpProxy`, `httpsProxy`, `ftpProxy`, `noProxy`, and `allProxy`, with control-free string values. URLs, user information, comma-separated exclusions, CIDRs, wildcards, and empty overrides remain literal. This is not an HTTPS-only proxy URL validator, and `noProxy` is not parsed as a URL.

Malformed, duplicate-key, oversized, or unsupported configuration is refused before registry login, staging builds/pushes, or Git/release publication. Diagnostics do not print proxy keys or values. Offline `--validate` deliberately does not inspect caller Docker configuration. The earlier builder bootstrap can have local effects; proxy validation does not promise otherwise.

Proxy URLs can contain credentials or sensitive hostnames. Never print complete Docker config, proxy environments, or build arguments for troubleshooting. The copy stays private and is removed with other run-owned temporary files on normal exit/failure/signals; caller registry `auths`, `credsStore`, and `credHelpers` are still excluded. Proxy values are not added to release-script command arguments, source contexts, public identity, or release notes. Displayed build logs filter known configured proxy values and their URL credential components; arbitrary encodings or values invented inside build steps cannot be universally detected. Treat logs as potentially sensitive before sharing them.

Preserving client build proxies does not configure daemon proxies, Git/curl host networking, DNS, certificate trust, or BuildKit server networking. Native forwarding and actual connectivity still require the separately authorized checklist; offline tests establish preservation and refusal boundaries only. See [Docker CLI proxy configuration](https://docs.docker.com/engine/cli/proxy/) for Docker's selection semantics.

## Publication and recovery

Publication locks `.release-operation.lock`, verifies source and target, inventories all final records and aliases, and classifies startup before any registry login or staging push. A failed/incomplete/oversized read is never permission to write. API inventories must end with a confirmed empty page; authenticated curl disables ambient config, follows no redirects, and refuses foreign registry token realms.

Fresh startup requires no requested Git tag/release and no version aliases for any image. Every `latest` is captured as its predecessor (including confirmed absence). All matching release-specific staging evidence is checked before the first build; verified parents are reused and missing members built once. Orphan/conflicting staging stops. Staging pushes are intermediate remote writes, even if final publication later fails.

Only after both images and their repository package associations verify does the command push one exact deterministic annotated Git tag binding commit, version, settings/helpers, notes, both certificates, platform, both digests, and predecessors. It promotes version and `latest` aliases from those digests without rebuilding, then creates a notes-only Gitea release. Fresh guards check the complete alias/tag and package state before each write; a confirmed promotion must remain at the prepared digest. Final verification checks all records, images, and associations, then prints immutable references, the release URL, and the repository Packages URL.

A fully completed retry verifies without build, login, tag push, promotion, or release creation. It ignores missing/foreign staging. A fresh attempt may reuse verified staging, but tag-only, release-only, orphan version aliases (even matching ones), conflicting identity, missing bound content, foreign final aliases, or partially promoted startup require manual review. Version aliases are never adoption authority. A lost response may be reconciled only against fresh exact evidence for that invocation's own attempted write.

There is no cross-service atomic transaction or exactly-once build promise. On failure, inspect the reported phase, known digest/alias map, confirmed and attempted package links, exact source/configuration, Git tag, release, and both image aliases. Do not blindly retry ambiguous states. Do not delete evidence, rewrite tags, force pushes, roll back aliases or package links, change settings to force success, or expect automatic repair. Manual completion needs separate review/authorization. There is no retention, package reassignment, image deletion, or rollback stage.

## HTTP error diagnostics

HTTP status refusals include the parsed numeric status, for example `Release stopped: Unexpected HTTP status: 403` or `Package/repository evidence unavailable (HTTP 404); no absence or mutation authority`. The status helps distinguish server responses but does not identify the failing endpoint or prove the underlying cause. A `403` can indicate insufficient permissions; inspect your existing user/repository/package access rather than bypassing authentication or TLS.

Diagnostics do not expose raw curl output, request URLs/query strings, credentials, credential paths, headers, payloads, or response bodies. Malformed status output remains `Invalid HTTP status`; transport failures and byte/time-limit refusals retain their own sanitized messages instead of claiming a valid server status. A valid HTTP response with malformed content is still a content/evidence failure, not an HTTP-status failure.

The transport status allowlist, strict ordinary API reads, normal registry `401` challenges and confirmed registry `404` absence, and refusal exception types remain unchanged. The initial named-package 404 fallback described above requires independent successful owner-list evidence; it does not accept arbitrary 404s or suppress permission errors. Status refusals do not authorize retry or repair. Repeated Bash error-handler output may still appear; it does not mean the release was attempted repeatedly. Diagnostics do not resolve server permissions or prove a successful publication. Release script hashes change with code, so preserve the existing identity rules rather than rewriting earlier release objects.

## Build logs

Both build modes display Docker Buildx step output live using `--progress=plain`, including the failing instruction's error text before the final command-failure summary. Phase messages report preflight, inventories, snapshot preparation, image build/reuse/verification, and publication stages. Displayed records and new phase messages go to stderr; helper decisions and final success summaries retain their existing stdout behavior. Completed publication retries report verification without rebuilding. API responses, login output, Git/curl stderr, and promotion command output remain private; there is no raw-log switch or persistent raw log file.

Filtering buffers each stdout/stderr record until newline, carriage return, or EOF, then strips terminal escapes/control characters, replaces known sensitive values, suppresses recognizable authorization headers/credential assignments, and replaces URLs with `[URL]`. Known values include the release token and Basic-auth encoding, supported effective Docker credentials, configured proxy values and encoded/decoded URL credential components, credential-file paths, and private run paths. Exact values and standard `quote`/`quote_plus` URL encodings are covered, not arbitrary transformations. Records larger than 64 KiB before filtering or 128 KiB after filtering are omitted with a fixed notice. An unterminated record appears only at EOF; stdout and stderr ordering relative to each other is not guaranteed.

Supported Docker `auths` entries are objects with optional string `auth`, `username`, `password`, `identitytoken`, and `registrytoken` fields. Empty objects and empty strings are valid. Nonempty `auth` must be strict standard Base64 decoding to UTF-8 `username:password`; passwords may contain colons. Control characters in supported fields or decoded credentials are refused because record delimiters must not split known sensitive values. The encoded value, decoded pair/password, and explicit supported password/token fields are filtered. Malformed supported fields refuse before the build without printing values. Build-only now reads its effective Docker config read-only with the existing 1 MiB bound and proxy validation to prepare filtering; a missing config is valid, but invalid, oversized, or unreadable config refuses before building. Publication reads its isolated config, not discarded foreign credentials. No external credential helper is called for filtering.

A separately supervised writer sends only sanitized records to stderr. Pending packets, including framing and unacknowledged in-flight records, are limited to 256 KiB; the oldest undelivered record has a five-second deadline. A full queue, stalled destination, broken pipe, or failed writer stops the operation without raw fallback. The capture loop continues supervising Docker while delivery is pending and cleans up both owned processes on refusal or interruption. Redirect output only to a consumer that drains it; these bounds apply to build-record delivery, not to arbitrary shell output or filesystem stalls elsewhere in the workflow.

Docker capture retains its existing 16 MiB stdout and 1 MiB stderr budgets and 7,200-second build timeout. Display filtering does not reset these budgets; exceeding them stops the operation rather than treating truncated output as valid evidence. Observer/sink refusals do not grant retry, repair, or lost-write reconciliation authority. The logging module participates in release-script identity, so old release objects must not be rewritten to fit changed tooling.

These protections are not universal secret detection. Downloaded setup scripts, custom encodings, unknown runtime credentials, and passwords held only by external helpers can escape known-value matching. Do not echo secrets or dump configuration in build steps, and inspect logs privately before sharing them. Offline tests verify filtering and supervision with synthetic data; they do not certify native Buildx behavior or production privacy for arbitrary build scripts.

## Offline verification

```bash
python3 -B -m unittest discover -s tests -v
bash -n build-all.sh
bash build-all.sh --validate
```

Tests use temporary Git repositories, test-owned version/tag/notes metadata independent of project releases, and stateful fake command/HTTP boundaries. They check two-image ordering, excluded-image noninterference, digest identities, credential/proxy isolation, package API contracts and authority, failure/retry guards, and zero unauthorized writes. First publication and read-only completed retries exercise both supported server contracts, including named-package 404s and independently verified owner searches. Evidence tests cover neighboring names, late contradictory targets, inaccessible resources, malformed or incomplete pages, duplicate identities, and shared inventory limits. Focused success, completed retry, and second-image refusal scenarios exercise two fixture versions without duplicating the full suite. Passing offline checks establishes local implementation acceptance only, not native Buildx behavior, real image toolchain correctness, live UI visibility, or production readiness.

## Native readiness checklist

Run only with separate user authorization and existing prerequisites. This implementation does not automatically run native builds or publication. Record command versions, selected context/host, builder driver/endpoint, each result, and all skipped connection variants without exposing credentials. Failed/skipped/unavailable checks leave that setup operationally unverified.

1. Record `docker version`, `docker buildx version`, `docker context show`, sanitized connection details, and `docker buildx inspect --bootstrap`. Confirm Linux AMD64 support and Docker-driver image-store routing for build-only. Do not switch/create builders implicitly.
2. In a private temporary test setup, compare plugin discovery/version before and during the same minimal-auth isolation used by `docker_auth` in `scripts/release_data.py`. Exercise a Buildx executable available only in the original config's `cli-plugins` and any configured extra plugin directory. Verify no caller auth/helper inventory is copied. Do not log in or contact production registries.
3. Compare context, Docker endpoint, TLS connection, and builder selection before/during isolation for host-only environment selection, explicit `default`, a nondefault context, and relative connection paths. Record which variants were actually exercised; do not infer untested TLS or remote behavior from a fake test.
4. Use a private temporary context and unique local image names to build a minimal parent with a unique marker, load it using the supported Docker driver, inspect its ID, then build a child using the checked local tag as `BASE_IMAGE` and `--pull=false`. Verify the parent ID is unchanged before/after the child build, the child's filesystem contains that marker rather than a stale parent marker, and the child parent label records that ID. Use no production tags or pushes; only remove the exact test-owned files/images after inspection and authorization.
5. With a separately selected container-backed builder, verify build-only refuses before any build. Restore any explicitly changed selection yourself; the script must not switch it. Record the actionable refusal.
6. With synthetic, noncredential-bearing proxy settings and disposable local image names, compare default and per-daemon proxy build-argument behavior before/during the same private-auth isolation. Exercise explicit empty values and `noProxy` exclusions. Check only presence/expected-match booleans inside a minimal build; never dump proxy environments or full config, put proxy URLs in command arguments, or persist values in image labels, files, or release metadata. Record sanitized outcomes and untested endpoint variants. Do not use production login/pushes; real connectivity needs a separately approved test endpoint.

A passing smoke checklist does not authorize or certify real publication. Actual two-image builds and production publishing need separate approval. Mutable downloaded setup scripts/packages mean source/digest identity is not reproducible bytes or runtime proof.

## Reference and limits

The local release code adapts [container-release-template](https://git.lan/dev/container-release-template) 0.4.0, inspected at commit `1d051b36888fd64d9bfcd49e8e09f504943b6a1a`. Its two-image identity distinguishes post-promotion alias expectations and verifies package associations. It preserves config-local plugin search paths instead of copying the reference's documented plugin-discovery omission. Native readiness still requires the checklist.

Package contracts were characterized against upstream tags [`v1.24.7`](https://github.com/go-gitea/gitea/tree/v1.24.7) and [`v28.2.0`](https://github.com/go-gitea/gitea/tree/v28.2.0): API schemas (`templates/swagger/v1_json.tmpl` and `templates/swagger/v1-swagger.generated.json`, respectively), `modules/structs/user.go`, `modules/structs/package.go`, `routers/api/v1/packages/package.go`, `routers/api/v1/api.go`, `services/context/package.go`, `services/convert/user.go`, `services/convert/package.go`, `models/packages/package_version.go`, `models/perm/access/repo_permission.go`, and `services/packages/package_update.go`. The response structs emit explicit false status flags and an explicit null repository rather than omitting these fields. `ListPackages` and `SearchVersions` apply owner/type/name/internal-version filters without silently omitting version rows by repository access; conversion can filter the repository field rather than the version. Routing requires authentication, package scope, owner package read access, and the public-only token check. Owner listing avoids the named-package resolution introduced in the newer middleware. Version strings are an operational compatibility check, not cryptographic proof of the deployed binary or arbitrary fork behavior.

Each HTTPS/manifest body is bounded at 4 MiB; config/token bodies at 1 MiB; headers, notes, and annotations at 64 KiB; Git advertisements at 16 MiB. Inventories share 1,002-page, 100,000-item, 64 MiB, and 600-second budgets. Reads time out after 60 seconds and builds after 7,200 seconds. Process output is bounded while receiving, not truncated into valid evidence. Only filtered Docker build records are displayed; other raw command stderr and authenticated response bodies remain private. These bounds do not limit Docker storage use or arbitrary Git pack storage.
