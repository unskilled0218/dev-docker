## scope

Update the root `build-all.sh` build and publication process using `https://git.lan/dev/container-release-template` version 0.4.0, inspected at commit `1d051b36888fd64d9bfcd49e8e09f504943b6a1a`, as a reviewed reference rather than a runtime dependency. Adapt its Bash-first, explicit-configuration, committed-source, digest-verified release model to this repository's five images. Keep implementation limited to the build/release entry point, focused helpers and settings, version and release notes, dependency-image arguments, tests, and release documentation. Do not change application setup, Compose files, `command.md`, or unrelated user work. This task only writes this plan; it does not implement or publish anything.

## Implementation Plan

### 1. Define the adapted release contract

- Keep `bash build-all.sh` as the public entry point. No arguments publishes the configured version; `--validate` performs side-effect-free local validation; `--build-only` builds local images without publication; `--help` and retained `-h` describe the contract. Reject unsupported combinations before external effects.
- Add root `VERSION` containing strict `MAJOR.MINOR.PATCH`, derive `v<VERSION>`, and require committed matching release notes for publication. Retain one positional tag as a deprecated compatibility assertion: `bash build-all.sh v<VERSION>` publishes only when the tag exactly matches the configured version; `bash build-all.sh --build-only v<VERSION>` and the reversed argument order build locally under the same check. No positional tag means the configured version. Reject mismatched tags, including explicit `latest`, duplicate tags/flags, unknown flags, or combining help/validation with another mode or a tag. Never silently rewrite a requested tag. Choose the initial version after checking existing repository tags/releases; do not overwrite existing history.
- Add `scripts/release.json` and focused Bash/Python-standard-library helpers under `scripts/`. Configure the actual `https://git.lan`, `dev/dev-docker`, login, notes path, token path, certificate path, and all five image names explicitly. Never inherit the template's Hello World image or publish target.
- Model the ordered image graph as `my-base` from `Dockerfile/base.Dockerfile`, `npm-non-root` from base, `android-dev` from npm, and `tauri-dev` plus `switchboard` from Android. Validate duplicate names, unknown keys, path escapes, mismatched registry/owner scopes, and malformed configuration before execution.
- Configure only `linux/amd64` initially. The current Switchboard Java path and downloaded Android/Watchman tooling are architecture-specific; multi-platform enablement and toolchain repair are separate work.

### 2. Add local validation and publication preflight

- Make `--validate` check settings, graph, version, notes, and required source paths without reading credentials, contacting services, invoking Docker, or creating locks/temp state. Help must need only Bash.
- For publication, require Bash, Python 3.11+, Git, curl, Docker Buildx, a builder advertising the configured platform, trusted HTTPS, and a clean, already-pushed `main`. Verify effective fetch and push targets and exact remote main before registry writes; do not push source automatically.
- Use a checkout-local lock and private run-owned temporary directory, with explicit exit/signal cleanup. Ignore only new runtime state paths. Recheck captured source and configuration before publication writes.
- Retain `FORGEJO_TOKEN_FILE` and `FORGEJO_USERNAME` as deprecated compatibility overrides, with explicit precedence: nonempty `GIT_TOKEN` then nonempty `FORGEJO_TOKEN_FILE` then configured `token_file`; nonempty `GIT_USERNAME` then nonempty `FORGEJO_USERNAME` then configured `username`. These token variables contain file paths, never token values. Configure this repository's token default as the existing `~/.config/forgejo/forgejo-token`, not an unannounced switch to the reference's `~/.config/git/token`; users can configure either path. Document precedence and migration and test both variables set, each set alone, and empty values. Require a readable, non-symlink, user-owned private token file outside the repository; do not log its contents or pass token values in arguments.
- Preserve `BUILD_CERT_FILE` and the current certificate default. Pass the selected token only through stdin for registry login and the existing `forgejo-token` BuildKit secret for the base build. Build-only still requires this build secret but must not log in or call publication APIs.
- Isolate registry auth without losing the caller's Docker host/context, TLS metadata, Buildx state, or plugin discovery. Resolve the reference's documented config-local Buildx plugin issue rather than copying it. Preserve the selected builder for publication; build-only also preserves selection but refuses unsupported drivers instead of switching builders. Never install certificates, privileged emulation, or other system dependencies automatically. Native preservation claims require the operational readiness gate below, not only fake-port tests.

### 3. Build the five-image dependency graph

- Add an `ARG BASE_IMAGE` before each dependent Dockerfile's `FROM`, preserving its current local `:latest` parent as the default. Release builds override this argument with the verified parent `registry/owner/image@sha256:...`, never a mutable local tag.
- Export only the captured committed source into the private publication build context, then inject the selected certificate. Never copy worktree files, ignored/untracked secrets, or the credential into that context. Hash the certificate as part of release identity because it is an external build input.
- Build each image once into a release-specific staging tag using Buildx, with source/version/revision labels and metadata capture. Verify its digest, platform, and configuration labels before building descendants. Track the digest map for the entire graph.
- Preserve local `image:latest` availability in `--build-only` using ordered Buildx builds with `--load` on AMD64. Before any build, inspect the selected builder and require the `docker` driver attached to the selected Docker endpoint's image store, with the configured platform advertised. Refuse `docker-container`, Kubernetes, remote, or unrecognized drivers with instructions to select a supported Docker-driver builder; never switch/create a builder or fall back to registry pushes. Verify each loaded parent's image ID and platform in that store before building its children, and confirm children use the just-built parent rather than a stale local or registry image. This explicit development mode may use current Dockerfiles without clean-main or remote checks; it still validates arguments, settings, required inputs, and dependencies. Qualify this native image-store behavior through the smoke checklist before declaring it supported operationally.
- Do not promote any public `latest` aliases, create a Git tag, or create a release until all five staging images verify. Staging pushes are unavoidable intermediate remote writes and must be reported as such on failure.

### 4. Publish and verify one release for the image set

- Adapt the reference's bounded HTTP/registry/Git reads and strict JSON handling. Treat malformed, truncated, failed, or incomplete inventory reads as refusal, never evidence of absence. Disable ambient curl configuration, redirects for authenticated calls, and credential forwarding to foreign registry token realms.
- Complete a read-only startup inventory of the Git tag, Gitea release, all five requested version aliases, and all five `latest` aliases before any staging push, login, tag push, or alias promotion. Inspect release-specific staging evidence only after this inventory classifies the invocation as eligible for a fresh attempt. Classify the complete set, not one image at a time; a conflict on Switchboard must block all writes just as a conflict on base would. Apply this state matrix:
  - Fresh: tag and release absent, every requested version alias absent, and all `latest` reads conclusively present or absent. Capture each `latest` predecessor, including absence, before staging. Missing staging is build permission only in this otherwise fresh state.
  - Staging retry: the same fresh final-record/alias state, with any existing release-specific staging objects matching captured source/configuration identity and verified platform/labels/digests. Reuse only matching evidence, build missing graph members, and refuse conflicting or unverifiable staging. Staging is not permission to adopt a preexisting version alias.
  - Completed: tag and release both present and their complete identity/body match; all five immutable images and version/`latest` aliases equal the annotation-bound digests. Verify without builds, login, promotions, tag pushes, or release writes. Missing or foreign staging is irrelevant and must not be looked up in this branch; first classify final records/aliases, then read staging only for an eligible fresh attempt.
  - Refusal: tag-only, release-only, any preexisting requested version alias without a completed matching publication, conflicting identity, incomplete reads, missing bound content, or any partially promoted final state. Even an apparently matching orphan version alias grants no adoption authority. Report exact known state for manual review and perform no writes.
- Capture predecessor aliases for all images before staging. Bind one deterministic annotated Git tag to source, version, settings/helper hashes, notes hash, certificate hash, platform, all five image digests, and predecessors. Push only the exact non-force tag.
- Before every staging/tag/alias/release write, freshly verify source, settings, final records, and the complete expected version/`latest` alias set under the current invocation's state. Version aliases remain absent until this invocation creates and confirms them; afterward they must equal their prepared digest. A lost write response can transition state only on fresh exact confirmation of that attempted write, never on arbitrary matching remote state. Before each promotion, verify the exact confirmed Git tag. Unpromoted `latest` aliases may equal their captured predecessor or prepared digest; once promoted, an image must remain at its prepared digest. This avoids the reference's documented post-promotion predecessor-acceptance flaw. Checks reduce races but cannot exclude another writer between a check and mutation.
- Promote verified digests to version and `latest` aliases without rebuilding, refusing any conflicting version alias. Create one Gitea release with the committed notes only after every intended alias verifies. Verify the tag, release body, immutable digests, and aliases again before returning success; print all image references and the release URL.
- On retry, reuse staging only when complete identity and image evidence match. For a fully completed publication, verify without building or writing. Refuse tag-only, release-only, conflicting, missing-content, or partially promoted startup states requiring manual review. Do not force tags, repair remote records, delete images, roll back aliases, or perform retention cleanup.
- Reconcile a lost write response only against fresh exact evidence within the same invocation. Report the failed phase and known image/alias state without leaking credentials. A checkout lock does not exclude other publishers; document the requirement for one operator across the image set.

### 5. Test failures and document operation

- Extend `tests/test_build_all.py` and add focused helper/publication tests with temporary repositories and fake Git, curl, Docker, and registry responses. Fix stale four-image assertions: the script already includes Switchboard, while the tests and release guide omit it.
- Cover all five images, graph ordering, digest-bound parents, labels, certificate/secret handling, build-only local tags, paths containing spaces, and invocation outside the repository. Verify all staging builds precede final publication.
- Cover strict configuration/version/notes validation, clean and pushed source checks, target mismatch, missing platform/tools, token permissions, Docker connection/plugin preservation, lock contention, and cleanup on failure/signals.
- Add explicit compatibility tests for all retained/deprecated/rejected invocations and credential precedence. Use stateful Docker fakes to distinguish a Docker-driver image store from a container-backed builder; assert unsupported-driver refusal before builds and no fallback pull of a wrong parent.
- Exercise staging/build/push failures, conflicting aliases, failed/oversized inventory reads, lost write responses, completed no-op retries, ambiguous partial states, changed confirmed tags, and a promoted alias reverting to its predecessor. Assert no subsequent unauthorized writes or rollback.
- Cover every startup state-matrix branch with stateful remote fakes, including a conflicting fifth-image version alias, a matching orphan alias, incomplete fifth-image inventory, partially published aliases, and completed verification with absent/foreign staging. Assert zero publication writes for every startup refusal, not merely a nonzero exit.
- Update `docs/image-releases.md` for configuration, credential migration, versioned publication, validation, build-only, all five images, prerequisites, trust, retry limits, and recovery. Keep `README.md` brief with a dedicated documentation link. Include a table of contents when creating Markdown files.
- Run `python3 -B -m unittest discover -s tests -v`, shell syntax checks for `build-all.sh` and new shell helpers, and `bash build-all.sh --validate`. Do not run a real release or install missing prerequisites; report any missing dependencies to the user.
- Write a separate opt-in native Buildx smoke checklist in `docs/image-releases.md`. Run it only with separate user authorization and available prerequisites: compare plugin discovery/version with a Buildx binary installed only in the original Docker config; verify the selected host/context, TLS connection, and builder endpoint before and during private-auth isolation without registry login; build a tiny local parent/child pair with a unique parent marker under a supported Docker-driver builder and verify the marker in the resulting child; verify a selected container-backed builder is refused before a build. Use temporary inputs and uniquely named test images, no production publication, no implicit builder switching, and no broad cleanup. Record command versions, driver/endpoint, results, and untested connection variants without recording secrets. This plan update does not execute those checks.

## Acceptance Criteria

### Local implementation acceptance

- Root `build-all.sh` supports the documented modes and explicit repository-specific settings without fetching executable release code at runtime.
- All five images build in dependency order; release children consume verified parent digests, while build-only preserves existing local names and Dockerfile defaults.
- Publication uses committed source, one version, one identity-bound tag/release, verified staging digests, and guarded final aliases. Failure never authorizes force, deletion, rollback, or silent repair.
- Validation has no credential or external side effects. Build-only performs no registry login, push, remote Git mutation, or Gitea release request.
- Credentials remain outside source contexts, logs, committed files, image layers, and persistent Docker auth. Existing certificate trust and Docker routing remain intact.
- Tests cover five-image success and negative/retry paths, and all local verification commands pass. Mocked results are not presented as live build or publication proof.
- Offline tests prove pre-write classification of every final alias and explicitly reject unsupported build-only drivers, orphan aliases, and conflicts on the fifth image before writes. Native store/routing/plugin guarantees remain provisional until the operational gate passes.
- Documentation lists retained and deprecated CLI/credential interfaces, intentionally rejected mismatched tags, precedence, AMD64-only support, supported build-only drivers, non-atomic multi-image publication, and manual handling of uncertain states. Existing credential defaults remain unchanged.

### Operational readiness gate

- Local implementation acceptance may complete without Docker access; it must label native Buildx plugin discovery, routing/TLS behavior, and parent-image resolution as unverified until the separately authorized native smoke checklist passes for the supported setup.
- Record smoke results separately from fake-port tests. Failed, skipped, or unavailable checks block operational-readiness claims for that setup, not completion of offline implementation work. No production release is authorized by a passing smoke checklist.

## Risks And Decisions

- The reference supports one image and exactly two platforms; copying its schema or running it five times would not provide one coherent release. Extend its identity and guards to the full graph, with explicit AMD64-only scope.
- Gitea, Git, and five registry aliases cannot be updated atomically. Failures can leave staging images, a tag, or some promoted aliases. Preserve evidence and stop; no automatic rollback or claim of transaction atomicity.
- The reference explicitly documents unresolved alias-guard and Buildx discovery warnings. The adaptation must cover both with tests before claiming readiness.
- Review A1 is resolved by retaining the selected builder and refusing non-Docker drivers in build-only before builds; supporting other drivers without publication is deferred. Review A2 is resolved by complete startup classification and per-write guards across all version and `latest` aliases, with no orphan-alias adoption.
- Review C1 is resolved by keeping legacy credential overrides/defaults and retaining positional tags only as exact configured-version assertions; arbitrary historical tags are intentionally rejected to preserve one release identity. Review T1 is resolved by separate offline acceptance and an opt-in native readiness gate; neither this plan nor fake-port success certifies a live Docker setup.
- Existing Dockerfiles download mutable remote scripts and packages. A captured source commit and verified output digest establish release identity, not reproducible bytes or runtime/toolchain correctness. Repairing existing image setup is outside this task.
- Base credentials are still required because the current Dockerfile requests a BuildKit secret, even though its final secret-mounted command only creates a directory. Do not redesign this unrelated setup in the release migration.
- Real image builds and publication require separate user-authorized verification with provisioned credentials, Docker, registry access, and trusted certificates. This workflow must not install privileged host dependencies or publish during tests.
